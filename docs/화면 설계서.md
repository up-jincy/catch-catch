# 화면 설계서

고객 시그널 캐처(Customer Signal Catcher) 프론트엔드의 **정본 설계 문서**입니다.
화면을 추가하거나 고칠 때는 이 문서를 먼저 갱신하고 코드를 바꿉니다.

| 문서 | 역할 |
| --- | --- |
| **이 문서** | 개발 정본. 구조, 계약, 화면별 상세 설계, 규칙 |
| `docs/frontend-screen-spec.html` | 팀 공유용. 왜 이렇게 정했는지와 폐기한 대안 |
| `docs/spec.md` | 해커톤 참가신청서 |
| `docs/api-endpoints.md` | 백엔드 API 목록 |

기준 커밋: `2af266e` · 상태: **Mock 구동 · 백엔드 미연결**

## 1. 아키텍처

### 1.1 라우트

라우트는 **두 개뿐**입니다.

| 경로 | 렌더 | 비고 |
| --- | --- | --- |
| `/` | `SignalCatcherApp` | 새 화면. 아래 모든 내용 |
| `/legacy` | `CustomerIntelligencePage` | 동료의 기존 Working Demo. 손대지 않음 |

**화면 4개는 라우트가 아니라 `phase` 상태로 전환합니다.** 라우트를 쪼개면 완료
연출(하트)이 라우트 경계에서 끊기기 때문입니다. 대신 History API 로 URL 만
동기화해 새로고침과 뒤로가기를 살립니다(§3.5).

### 1.2 데이터 흐름

```
app/page.tsx
     │
     ▼
SignalCatcherApp ──── useDemoOptions()      URL 쿼리 파싱  (데모 전용, §7)
     │           └─── useCatchSession()     상태 엔진
     │                     │
     │                     ▼
     │                CatchSession  ◀── 화면이 소비하는 유일한 계약
     ▼
session.phase 로 화면 교체
     │
     ├─ ask       AskScreen
     ├─ catching  CatchingScreen
     ├─ result    ResultScreen
     ├─ trace     TraceScreen
     └─ action    ActionScreen

useExperiments()  ← CatchSession 밖. localStorage 에 보관
```

화면 컴포넌트는 **`CatchSession` 을 받아 그리기만 합니다.** 데이터를 어디서
가져오는지 모릅니다. 그래서 백엔드를 붙일 때 화면을 고칠 필요가 없습니다.

## 2. 상태 계약

### 2.1 phase 전이

```
        start()              settle()            openTrace()
 ask ──────────▶ catching ──────────▶ result ──────────────▶ trace
  ▲                  │                  │  │                    │
  │                  │ retry()          │  │ openAction()       │
  │                  ▼                  │  ▼                    │
  │             (실패 시 멈춤)           │ action   closeTrace()  │
  └───────────── reset() ───────────────┴──┴────────────────────┘
```

- **`catching` 은 되돌아갈 지점이 아닙니다.** History 에 남기지 않습니다.
- 실패해도 화면을 자동으로 바꾸지 않습니다. `catching` 에서 멈춰 세웁니다(§3.2).

### 2.2 `CatchSession`

화면이 소비하는 **유일한 계약**입니다. (`state/types.ts`)

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `phase` | `"ask" \| "catching" \| "result" \| "trace"` | 현재 화면 |
| `question` | `string` | 사용자 질문 |
| `stages` | `Stage[]` | 5단계 진행 상태 |
| `activeStage` | `StageKey \| null` | 진행 중 단계 |
| `clarification` | `ClarificationPrompt \| null` | 있으면 심문 모달 |
| `outcome` | `"completed" \| "degraded" \| "failed" \| null` | 종료 상태 |
| `report` | `CatchReport \| null` | 결과 · 검증 기록 데이터 |
| `failureReason` | `string \| null` | 실패·범위밖 안내 문구 |
| `suggestedQuestions` | `string[]` | 범위 밖일 때 대안 질문 |

`Stage` 는 `{ key, label, short, event, detail, status }` 입니다.
`event` 는 대응하는 Canonical Run Event 이름으로, **화면에 노출하지 않고
백엔드 매핑 참고용**으로만 둡니다.

### 2.3 `CatchReport`

결과 화면과 검증 기록이 함께 씁니다.

| 필드 | 쓰이는 곳 |
| --- | --- |
| `headline` · `headlineCount` · `headlineTrailer` | 결과 헤드라인 |
| `summary` · `segmentLabel` | 요약, Action Preview 대상 |
| `metrics: AnalysisMetricFact[]` | 핵심지표 카드. `NaN` 이면 "근거 부족" |
| `signals: AnalysisSignal[]` | 시그널 기여도 바 |
| `journey: JourneyNode[]` · `lanes: JourneyLane[]` | 시그널 저니 |
| `findings: LedgerClaim[]` | 검증된 발견 · Claim Ledger |
| `actions: CatchAction[]` | 다음 행동. `keywords` 가 있으면 실행 화면 |
| `limitations: string[]` | 부분 캐치 패널, 검증 기록 |
| `planSteps: PlanStep[]` | 분석 로그 탭 |
| `score: TraceScore` | 검증 기록 스코어카드 |
| `datasetVersion` · `adapterVersions` | 재현 정보 |

`JourneyNode` 는 백엔드 `JourneyEvent` 를 확장합니다.
`lane`(레인), `column`(시간순 위치), `intensity`(0~1 강도),
`tone`(`signal` / `negative` / `repeat`), `insight`(AI 해석)를 얹습니다.

### 2.4 컨트롤러 API

`useCatchSession()` 이 반환합니다.

| 항목 | 용도 |
| --- | --- |
| `session` | 위 계약 |
| `bursting` | 완료 직전 하트 연출 구간 |
| `flatline` | 진행이 멎은 구간 (심박 평선) |
| `log` | 지나간 진행 문장 누적. 화면은 뒤 6줄만 |
| `start(question)` | 분석 시작 |
| `retry()` | 실패 화면에서 같은 질문 재실행 |
| `answerClarification(answer)` | 심문 모달 답변 |
| `restore(view, question)` | 새로고침·뒤로가기 복원 |
| `openTrace()` / `closeTrace()` | 검증 기록 전환 |
| `reset()` | 첫 화면으로 |

## 3. 화면 설계

### 3.1 질문하기 (`phase: "ask"`)

```
              고객은 말보다 먼저 신호를 보냅니다
            고객의 시그널을 찾아보세요          ← Gasoek One
                [데이터셋 5] [최근 14일]        ← 조건 토큰
   ┌──────────────────────────────────────────┐
   │ (+)  질문 입력…                      (🔍) │  ← 튜브
   └──────────────────────────────────────────┘
   [카드1] [카드2] [카드3] [카드4]              ← 제안 시나리오
```

| 요소 | 설계 |
| --- | --- |
| Placeholder | 페르소나별 질문이 타자 치듯 교체. 실제 `placeholder` 속성이 아니라 오버레이. 한 글자라도 입력하면 즉시 멈춤 |
| `+` 버튼 | 2depth 컨텍스트 메뉴. `데이터셋 >` / `기간 >` |
| 데이터셋 패널 | 연결된 소스가 **전부 켜진 상태**로 시작. 소스별 설명·주제 뱃지·보유 기간 노출. `search_history` 는 해제 불가 |
| 기간 패널 | 칩(최근 7/14/30일) + **직접 선택**(시작일·종료일 date input, 적재 구간 밖 선택 불가) |
| 제안 카드 | 페르소나 태그 + 라벨 + 질문 전문(3줄 클램프) |
| 안내 박스 | 범위 밖 질문으로 되돌아왔을 때. **경고색이 아니라 브랜드 톤(마젠타)** — 오류가 아니라 Agent 의 안내이기 때문 |

- 제출: 클릭 또는 `Enter`(Shift+Enter 는 줄바꿈)
- 되돌아와도 **질문과 조건은 보존**합니다.

### 3.2 캐치하는 중 (`phase: "catching"`)

```
              ( 최근 로밍을 알아보는 고객들은… )   ← 질의 바 (상단 고정)

   ━━╱╲━━━━━╱╲━━━━━╱╲━━━━┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈
     │        │        │        │        │
    목표     계획     분석   인사이트   검증

           ✓  앱 행동로그를 고객 단위로 잇는 중    ← 흐림
           ✓  가입 상태를 대조하는 중             ← 흐림
       [분석] 상담 이력까지 연결하는 중            ← 선명
```

**심박 라인이 곧 스테퍼입니다.** 별도 스텝 인디케이터를 두지 않습니다.

| 요소 | 설계 |
| --- | --- |
| 질의 바 | 질문은 콘텐츠가 아니라 맥락이므로 중앙 스택에서 빼 상단에 고정 |
| 심박 | 박동 하나 = 단계 하나. 끝난 구간은 마젠타로 남고, 진행 중 구간은 그 단계 소요시간에 맞춰 실시간으로 그려짐. 아직 안 온 구간은 회색 평선 |
| 스테퍼 라벨 | 각 박동 바로 아래 |
| 진행 로그 | 크레딧처럼 위로 흐름. **등속이 아니라 계단식** — 문장이 도착할 때만 한 줄 밀림. 현재 문장은 항상 같은 자리 |
| 로그 마스크 | 위로 지나간 줄은 잘리지 않고 서서히 지워짐. 창 높이 고정이라 심박이 흔들리지 않음 |
| 멈춤 | 심문 대기·실패 시 심박이 평선으로 떨어지고 회색으로 |

**단계별 체류 시간** (`state/mock.ts` 의 `STAGE_TICKS[].ms` 합)

| 단계 | 시간 | 성격 |
| --- | --- | --- |
| 목표 | 1.3초 | 훑는 속도 |
| 계획 | 0.9초 | 훑는 속도 |
| 분석 | 1.9초 | 5문장이 후루룩 |
| **인사이트** | **2.1초** | 읽는 속도 |
| **검증** | **3.5초** | 마지막 문장 혼자 **2.4초** |

총 10.9초. 앞 세 단계 38%, 뒤 두 단계 62%. 데이터를 훑는 구간은 기계 속도로
흘려보내고 결론과 검증만 잡아 둡니다. **이 비율을 바꿀 때는 검증 마지막
문장이 2초 아래로 내려가지 않게 합니다** — 우리 팀 차별점이 드러나는 문장입니다.

**로딩 화면은 기본/분석가 모드를 따르지 않습니다.** 같은 화면이 모드에 따라
달라 보이면 혼란만 줍니다. 원본 값은 결과 화면과 검증 기록에서 봅니다.

#### 심문 모달 (`clarification`)

진행이 멎은 순간을 약점이 아니라 **단서를 좁히는 장면**으로 연출합니다.

1. 심박이 평선으로 떨어지고 화면이 어두워짐
2. Agent 질문이 타이핑되며 등장 (첫 화면 placeholder 와 같은 모션 언어)
3. `#ff2e98` 블록 커서 + 모노 입력창 + `>` 프롬프트
4. 답변 전송 → 심박이 다시 뜀

- 헤드라인 "잠깐, 하나만 더 확인할게요" 는 **Gasoek One**, Agent 질문은 본문
- 브라우저 기본 `alert`/`confirm` 금지. focus trap 을 건 커스텀 dialog
- 백엔드가 답을 기다리므로 "나중에 답하기" 는 두지 않음

#### 실패 (`outcome: "failed"`)

**화면을 자동으로 바꾸지 않습니다.** 자동으로 첫 화면에 돌려보내면 사용자가
왜 돌아왔는지 알 수 없습니다.

- 평선이 된 심박이 **어느 단계에서 끊겼는지 그대로** 남음
- `연결 끊김` 앰버 배지 + 사유 + `[다시 캐치하기]` `[질문 바꾸기]`
- 모달로 덮지 않습니다. 평선을 가리기 때문입니다.

### 3.3 캐치 결과 (`phase: "result"`)

```
                                        [부분캐치]      [기본|분석가]
   단기 일본 여행 로밍을 고르지 못한 고객
   328명을 찾았어요                              ← Gasoek One
   요약 문단…
   [시그널 고객 328명] [평균 반복검색 3.4회] [상세조회후 미가입 71%] [재검색까지 4.2일]
   일본 로밍 반복 검색  ▇▇▇▇▇▇░░░░  34%
   ─────────────────────────────────────────
   시그널 저니 | 인사이트 & 액션 | (분석 로그)
   ─────────────────────────────────────────
```

| 요소 | 설계 |
| --- | --- |
| 헤드라인 | `{headline}` + `{headlineCount}명을 찾았어요`. 숫자만 마젠타 |
| 부분 캐치 배지 | `outcome === "degraded"` 일 때. 누르면 `limitations` 패널 펼침 |
| 지표 카드 | `value` 가 `NaN` 이면 **숫자를 지어내지 않고** 점선 테두리 + "근거 부족" |
| 모드 토글 | 기본 / 분석가. 정보 밀도만 바꿈 (§4.3) |
| 탭 | 시그널 저니 / 인사이트 & 액션 / **분석 로그(분석가 모드만)** |
| 하단 | `이 결론이 나온 과정 보기 →` · `새로 캐치하기` |

**스테퍼가 아니라 탭입니다.** 스테퍼는 "순서대로 완료해야 함"을 뜻해서 조회
화면과 맞지 않습니다.

#### 탭 1 · 시그널 저니

```
   ▶ ━━━━━━━━━━━━━━━●━━  3/8
   ┌─────────────────────────────┐ ┌──────────────┐
   │      8/12  8/12  8/13 …     │ │ 8/12 09:14   │
   │ AI검색  ●────●          ●   │ │ 일본 로밍     │
   │ 피드백        │      ●      │ │ 데이터 원천… │
   │ 앱 행동       └──●───┘      │ │ AI 해석…     │
   │ 가입정보         └──●       │ │ [원본 근거]  │
   │ 상담                    ●   │ └──────────────┘
   │ 시그널 강도  ╱╲╱╲╱          │
   └─────────────────────────────┘
```

- **격자는 스윔레인, 그 위를 선 하나가 시간순으로 관통**합니다. 레인을 넘나드는
  지그재그가 곧 cross-channel 이라는 주장의 시각적 증거입니다.
- 열은 날짜가 아니라 **이벤트 순서**입니다. 선이 항상 왼쪽에서 오른쪽으로 흐릅니다.
- `▶` 재생: 노드가 시간순으로 켜지며 선이 그려지고, 우측 패널이 따라 바뀝니다.
  스크러버로 임의 지점 이동 가능.
- 하단 강도 곡선은 `signals[].contribution` 기반입니다. **감정 곡선처럼 지어낸
  값을 쓰지 않습니다.**
- 노드 클릭 → 우측 패널 → `원본 근거 보기` → 근거 드로어

> 디자인 씽킹 유저 저니맵의 격자는 채택하지 않습니다. 감정 칸을 채우려면
> 데이터에 없는 값을 지어내야 하고, 이는 "모든 주장은 원본 데이터로 검증된다"는
> 우리 원칙과 충돌합니다. 강도 곡선과 국면 구분만 데이터로 뒷받침될 때 가져옵니다.

#### 탭 2 · 인사이트 & 액션

- **검증된 발견**: `findings` 중 `verdict === "passed"`. 각 문장에 근거 칩.
  분석가 모드에서는 `rejected` 도 사유와 함께 노출.
- **다음 행동**: `actions`. `keywords` 가 있는 항목만 `추천검색어 적용하기`
  버튼을 갖고, 나머지는 `다음 단계` 라벨.

#### 탭 3 · 분석 로그 (분석가 모드만)

`planSteps` 를 순서대로. `revisedFrom` 이 있으면 "계획 수정됨"을 앰버로 노출합니다.
**감추지 않습니다** — 스스로 계획을 고치는 Agent 라는 증거입니다.

#### Action Preview (추천검색어 적용)

신청서 9장의 Mock Interaction 입니다.

`추천검색어 적용하기` → 설정 화면(키워드 체크) → `N개 적용하기` → 적용 중 →
적용 완료. 완료 화면에 **"실제 운영 시스템에는 반영되지 않았어요"** 를 명시합니다.

### 3.4 검증 기록 (`phase: "trace"`)

우리 팀이 다른 팀과 갈리는 지점을 드러내는 화면입니다.

| 블록 | 내용 |
| --- | --- |
| 스코어카드 | 검증 통과 주장 12/14 · 근거 커버리지 · 분석 스텝 · 사용 소스 · **계획 수정 횟수** · 소요 시간 |
| 계획 수정 안내 | `planRevisions > 0` 이면 무엇이 부족해 고쳤는지 문장으로 |
| Claim Ledger | 주장마다 `CLAIM → FACT → SOURCE → EVIDENCE` 계보. **탈락한 주장도 사유와 함께** |
| 재현 정보 | `datasetVersion`, 소스별 adapter 버전 |
| 확인하지 못한 것 | `limitations` |

**탈락한 주장을 싣는 것이 이 화면의 핵심입니다.** 전부 통과한 리포트는
검증하지 않은 리포트와 구분되지 않습니다.

### 3.5 액션 (`phase: "action"`)

**Insight 는 누구나 낼 수 있습니다.** 차별점은 제안 이후에 있습니다.
분석 단계에서 주장을 원본 데이터로 검증하듯, 실행 단계에서는 **예측을 실측으로 검증**합니다.

| | 분석 단계 | 액션 단계 |
| --- | --- | --- |
| 무엇을 검증? | 주장을 원본 데이터로 | **예측을 실제 결과로** |
| 결과 | 14개 중 12개 통과 | **6개 중 4개 적중** |
| 숨기지 않는 것 | 탈락한 주장 2개 | **빗나간 예측 2개** |

한 페이지가 네 단계로 변신합니다. **페이지를 옮기지 않아 서사가 끊기지 않습니다.**

```
① preview   AS-IS ↔ TO-BE 시안 · 예상되는 변화 표 · [✨ 캐치한 대로 바꿔보기]
     ▼ 매직 연출 (1.9초)
② applying  마젠타 빛줄기가 TO-BE 를 훑고 새 항목이 하나씩 그려짐. AS-IS 는 물러남
     ▼
③ watching  "적용했어요. 7일간 지켜볼게요" · [⏩ 7일 뒤로 감기] → 타임랩스
     ▼
④ report    "예측 6개 중 4개가 맞았어요" · 지표별 예측 vs 실제 · [다음 액션 보기]
```

#### 세 단계가 같은 표를 공유합니다

수치 비교는 카드가 아니라 표가 맡습니다. 단계마다 **열만 바뀝니다.**

| 단계 | 표현 |
| --- | --- |
| 미리보기 | 표 — 지표 · 지금 · **예상** · 변화 |
| 관찰 중 | **스파크라인** — 큰 숫자 · 델타 · 7일 추이 · 목표 점선 |
| 리포트 | **스파크라인**(추이) + 표(채점) |

미리보기는 아직 관측된 값이 없어 표만 씁니다.
관찰 중과 리포트는 **시간에 따라 움직인 값**이 있으므로 스파크라인을 씁니다.
리포트에서는 **목표 점선과 실제 종착점의 거리가 곧 채점 결과**라 표보다 먼저 읽힙니다.
같은 컴포넌트를 쓰되 그리는 범위만 다릅니다 — 관찰 중은 재생 위치까지, 리포트는 끝까지.

역할이 겹치지 않게 나눕니다. **스파크라인은 추이(gain 3개), 표는 채점(6개 전부).**

#### 관찰 지표는 분석 도구의 관습을 따릅니다

큰 숫자 · 델타 · 스파크라인. Datadog · Grafana · Amplitude · Stripe 가 모두
같은 형태를 씁니다. 사람들이 이미 아는 형태여야 설명 없이 읽힙니다.

- 목표는 **점선 한 줄**. 값이 그 선을 넘었는지가 한눈에 읽힙니다
- 타임랩스를 재생하면 선이 왼쪽에서 오른쪽으로 그려집니다. 심박 라인과 같은 모션 언어입니다
- **시간 축은 스파크라인의 가로축이 이미 맡습니다.** 상단에 진행 바를 또 두면
  지표 그래프와 같은 언어로 보여 어지럽습니다. 날짜와 일차만 문장으로 둡니다

> 진행률 트랙(시작→목표 사이 위치)은 폐기했습니다. 그건 지표 추이가 아니라
> **프로젝트 진행률 UI** 이고, 7일치 시계열을 갖고 있으면서 한 점으로 뭉개는 표현입니다.

#### 좋아질 것 / 나빠질 수 있는 것

**좋은 것만 실으면 검증하지 않은 제안과 구분되지 않습니다.**
`Prediction.direction` 이 `gain` / `risk` 로 갈리고, 둘을 **같은 모양으로** 싣습니다.
각 예측에는 근거(`evidenceIds`)와 이유가 붙습니다.

| direction | 색 | 예 |
| --- | --- | --- |
| `gain` | **무채색** | 가입 전환율 12% → 18% |
| `risk` | 앰버 좌측 바 | 다른 로밍 상품 노출 -23%, 일본 외 목적지 정확도 -8%p |

`gain` 을 마젠타로 칠하면 TO-BE 시안의 마젠타와 경쟁해 둘 다 죽습니다.
표에서는 **구획과 좌측 바로 나누고 색은 위험에만** 씁니다.

#### 판정은 빗나간 쪽만 강조

적중은 기대대로이므로 조용합니다. **시선은 빗나간 예측으로 가야** “우리는 숨기지
않는다”가 읽힙니다. 빗나간 행만 앰버 좌측 바 · 앰버 수치 · 앰버 라벨을 갖고
사유가 지표명 아래 붙습니다.

#### 시안은 실제 구조를 따른 와이어프레임

픽셀까지 재현하지 않습니다. 실제와 조금만 달라도 거짓이 되고, 디테일이 많아지면
**무엇이 바뀌었는지가 묻힙니다.** 대신 **배치는 실제 구조를 그대로** 따릅니다.
어디에 뜨는지가 틀리면 시안이 전달하는 정보 자체가 틀린 것이기 때문입니다.

AI검색은 답변이 위, 입력창이 하단, 추천검색어가 입력창 바로 위에 뜹니다.
두 패널의 높이를 맞춰 입력창을 같은 자리에 고정하면
**빈 공간에 3줄이 들어차는 변화가 한눈에 읽힙니다.**
시안 아래에 “실제 화면 구조를 따른 와이어프레임입니다”를 명시합니다.

#### 매직 연출

심박 라인과 같은 “선이 지나간다” 언어를 씁니다.

1. 마젠타 빛줄기(`sweep`)가 TO-BE 패널을 좌→우로 훑음 (900ms)
2. 빛이 지나간 자리에 새 항목이 **220ms 간격으로 하나씩** 그려짐 (`draw`)
3. AS-IS 패널은 흐려지며 뒤로 물러남 (`recede`)

AS-IS / TO-BE 는 **위를 맞춰** 배치합니다. 검색어 줄이 나란히 놓여야 무엇이 늘었는지 바로 읽힙니다.

#### 타임랩스

`⏩ 7일 뒤로 감기` 를 누르면 420ms 간격으로 하루씩 감기며 지표가 움직입니다.

> **데모용임을 숨기지 않습니다.** 버튼 아래에
> “실제로는 7일을 기다려야 하지만, 데모를 위해 미리 준비한 데이터로 감아 볼게요” 를 명시합니다.
> 숨기면 속이려 한 것처럼 보이고, 밝히면 여기까지 설계했다는 뜻이 됩니다.
> 검증 기록에서 `dataset_version: synthetic-...` 을 당당히 노출하는 것과 같은 태도입니다.

#### AI 인사이트는 스파클로 구분합니다

리포트 마지막의 해석 문장은 **측정된 수치가 아니라 AI 가 만든 문장**입니다.
표·그래프와 성격이 다르므로 출처를 밝힙니다.

- SaaS 관습대로 **스파클 마크**를 씁니다. Notion AI · Linear · Figma 가 쓰는 그 신호입니다
- 이 화면에서 **면을 갖는 유일한 블록**입니다. 나머지는 표와 그래프뿐입니다
- 스파클은 **AI 산출물과 AI 실행 버튼에만** 붙입니다.
  다른 곳에 쓰면 “AI 가 만든 것”이라는 의미가 흐려집니다
- 이모지가 아니라 SVG 로 그립니다. 적용 버튼과 같은 마크를 씁니다

#### 채점 리포트 — 빗나간 예측이 다음 액션을 정당화한다

액션 3개를 독립된 항목이 아니라 **인과로 엮습니다.**

```
액션1 (추천검색어) 적용
   ↓
예측: 상담 인입 -37%    실제: -22%    ← 빗나감
   ↓
"검색은 줄었지만 상세페이지에서 여전히 이탈했습니다"
   ↓
액션2 (기간 선택 가이드)가 필요한 이유가 데이터로 증명됨
```

Agent 가 **자기 제안의 한계를 스스로 발견하고 다음을 제안**합니다.
신청서의 `Detect → Understand → Recommend → Act` 가 한 바퀴 돌아 다시 Detect 로 이어집니다.

#### 액션 하나만 깊게

`ACTION_PLANS` 에는 `search_keyword` 하나만 있습니다.
셋을 다 만들면 전부 얕아집니다. 나머지 둘은 결과 화면 카드로 두고,
리포트 마지막에서 액션2 로 이어지는 고리만 만듭니다.

## 3.6 실험 상태

실험은 **Run 하나보다 오래 삽니다.** `CatchSession` 밖의 `useExperiments()` 가
`localStorage` 에 보관합니다. 첫 화면으로 나갔다 와도, 새로고침해도 이어서 볼 수 있습니다.

### 동시 실험은 막지 않습니다

귀인이 깨지는 건 실험이 둘이라서가 아니라 **같은 고객 세그먼트를 건드릴 때**입니다.
로밍 담당자의 실험과 인터넷 장애 담당자의 실험은 대상이 달라 동시에 돌려도 문제없습니다.

**같은 `segmentLabel` 을 관찰 중일 때만** 적용 직전에 알립니다.

> **겹치는 실험이 있어요**
> `상황형 추천검색어` 가 같은 고객군을 이미 관찰 중이에요.
> 지금 함께 적용하면 지표가 움직여도 **어느 쪽 효과인지 구분할 수 없어요.**
> `[그래도 함께 적용]` `[진행 중인 실험 먼저 보기]`

막는 게 아니라 알리고 사용자가 정합니다. 세그먼트가 다르면 경고 자체가 뜨지 않습니다.

### 진입점은 둘, 목록 화면은 없다

```
상단 바 배지 ─────┐
                  ├──▶ 액션 페이지
액션 탭 카드 ─────┘
```

| 진입점 | 성격 |
| --- | --- |
| **상단 바 `⏱ 관찰 중 1` 배지** | 전역 접근. 상단 바는 `phase` 와 무관하게 항상 렌더되므로 **어느 화면에서 나가든 같은 자리**에서 복귀 |
| **결과 화면 액션 탭 카드** | 그 분석 안에서의 상태. 카드에 진행 바와 배지 |

**별도 목록 화면을 만들지 않습니다.** 배지 드롭다운이 관찰 중·완료를 모두 보여주고,
액션 탭 카드가 그 Run 의 실험 목록 역할을 합니다.
배지는 실험이 있을 때만 나타나고 없으면 자리도 차지하지 않습니다.

> 첫 화면 본문에 배너를 두는 안은 폐기했습니다. 그 자리는 `unsupported` 안내가 쓰는
> 자리라 의미가 겹치고, 입력창 바로 위 라운드 박스라 또 다른 입력으로 보입니다.
> 하단 플로팅 버튼도 폐기했습니다 — 우하단은 관습적으로 “새로 만들기” 자리입니다.

### 3.6.0 리포트는 스냅샷이지 대시보드가 아니다

액션을 적용하면 데이터가 바뀝니다. 그렇다고 **그 액션을 제안한 원본 리포트를
사후에 갱신하면 안 됩니다.** 갱신하는 순간 “이 결론이 나온 과정”을 재현할 수 없어지고
검증 기록이 거짓이 됩니다.

Run 은 이미 스냅샷으로 설계돼 있습니다 — `start_at` · `end_at` 이 고정이고
`dataset_version` · `adapter_versions` 가 박혀 있습니다.
`328명 / 71% / 4.2일` 은 틀린 값이 아니라 **그때는 맞았던 값**입니다.

진짜 문제는 “이 숫자가 언제 것인지 보이지 않는다”는 것이었습니다. 두 가지로 해결합니다.

| | 내용 |
| --- | --- |
| **기준 시점 명시** | 헤드라인 아래에 `2026.08.05 – 08.19 데이터 · 2026.08.19 분석` |
| **이후 변화 알림** | 실험이 있으면 상단에 “이 분석 이후 ~를 적용했어요. 아래 수치는 **적용 전 시점**의 값입니다” + 실험으로 가는 링크 |

리포트는 그대로 두고 **맥락만 얹습니다.** 관찰 중이면 “적용해 관찰 중이에요”,
끝났으면 “적용했어요”로 문구만 갈립니다.

최신 상태가 필요하면 **새로 분석을 돌리는 것**이 맞습니다. 그러면 새 Run 이 생기고
그것이 다음 액션의 근거가 됩니다. `Detect → Understand → Recommend → Act → Detect` 가
실제로 한 바퀴 돕니다.

### 3.6.1 화면 전환 시 스크롤

한 페이지에서 `phase` 만 갈아끼우기 때문에 **그대로 두면 아래쪽에서 누른 버튼의
스크롤 위치를 다음 화면이 물려받습니다.** `phase` 가 바뀌면 즉시 맨 위로 되돌립니다.
액션 화면 안에서 단계(`watching` · `report`)가 바뀔 때도 같습니다.

예외는 적용 연출 하나입니다. 적용 버튼은 화면 아래에 있어 연출이 시야 밖에서
일어날 수 있으므로, **시안이 이미 다 보이면 건드리지 않고 벗어난 만큼만** 옮깁니다.
`scrollIntoView` 는 재렌더와 겹치면 화면 끝으로 튀므로 명시 좌표를 씁니다.

### 3.7 URL 동기화

라우트를 쪼개지 않고 History API 로 상태만 반영합니다.

| URL | 화면 |
| --- | --- |
| `/` | 질문하기 |
| `/?view=result` | 캐치 결과 |
| `/?view=trace` | 검증 기록 |
| `/?view=action` | 액션 (미리보기·관찰·리포트) |

- 새로고침 시 로딩을 건너뛰고 **0.8초** 만에 복원
- 검증 기록 → 뒤로가기 → 결과 → 뒤로가기 → 첫 화면
- `catching` 은 기록하지 않음

> 백엔드 연결 후에는 `?view=result` 대신 **`/runs/{run_id}`** 같은 실제 run id
> 기반 URL 로 올려야 합니다. 지금은 Mock 이 하나뿐이라 파라미터로 둔 것입니다.

## 4. 공통 규칙

### 4.1 오버레이는 반드시 portal

근거 드로어 · 추천검색어 모달 · 심문 모달은 `Overlay.tsx` 를 거칩니다.

화면 전환 래퍼(`.enter`)는 `animation-fill-mode: both` 로 끝난 뒤에도
`transform` 이 남고, **transform 이 있는 조상은 `position: fixed` 의 기준점이
됩니다.** 그대로 두면 스크롤을 내린 상태에서 오버레이가 화면 밖에 그려집니다.

디자인 토큰이 `.app` 안에만 정의돼 있으므로 `document.body` 가 아니라
`.app` 안쪽의 `#catcher-overlay-root` 로 보냅니다.

> **새 모달·드로어·툴팁을 추가할 때 반드시 `Overlay` 로 감싸세요.**

### 4.2 서비스 마크는 한 곳만

돋보기 + 파형 + 하트 조합입니다. **돋보기 = 찾는다, 파형 = 시그널,
하트 = 찾았다.** 하트는 완료 연출에서 터지는 하트의 복선입니다.

- 노출은 **상단 좌측 서비스명 자리 한 곳뿐**입니다.
- 렌즈·손잡이는 놓인 자리의 글자색을 따르고 **하트만 마젠타**로 빠집니다.
- 캐치 버튼은 평범한 돋보기, 로딩 질의 바와 결과 헤드라인은 아이콘 없이 텍스트만.

로고를 반복하면 브랜드가 강해지는 게 아니라 닳습니다.

### 4.3 기본 / 분석가 모드

페이지를 나누지 않고 **같은 화면의 정보 밀도만** 바꿉니다. 결과 화면에만 적용됩니다.

| 요소 | 기본 | 분석가 |
| --- | --- | --- |
| 근거 칩 | 노출 | 노출 |
| 지표 카드 | 숫자와 라벨 | + `metric_key` |
| 탈락한 주장 | 숨김 | 사유와 함께 노출 |
| 분석 로그 탭 | 숨김 | 노출 |
| 저니 노드 상세 | 행동 요약 | + `source_id`, `event_type` |
| 로딩 화면 | — | **동일 (모드 미적용)** |

깊이는 3단입니다. **Tier 1** 근거 칩 → **Tier 2** 근거 드로어 → **Tier 3** 검증 기록.

## 5. 디자인 시스템

### 5.1 색 — LG유플러스 2025 리브랜딩

공식 5색 밖의 색은 만들지 않습니다. 파생값도 `color-mix` 로만 뽑습니다.
모두 `catcher.module.css` 의 `.app` 스코프에 있습니다.

| 이름 | HEX | 역할 |
| --- | --- | --- |
| Bright Magenta | `#ff2e98` | 강조 · 시그널 · 심박 · 검증 통과 |
| U+ Black | `#22171c` | 페이지 바탕 |
| U+ Gray | `#82817e` | 흐린 글자 |
| U+ Light Gray | `#f4f4ee` | 본문 글자 |
| U+ White | `#ffffff` | 마젠타 버튼 위 글자 |

**밝은 바탕을 쓰지 않습니다.** Light Gray 를 바탕에 깔면 마젠타가 막대·칩
정도로만 나타나 브랜드가 화면을 끌고 가지 못합니다. U+ Black 을 바탕으로,
Light Gray 를 글자로 쓰면 여전히 공식 5색인데 마젠타가 발광합니다.
본문 대비 13:1, 흐린 글자 4.6:1 로 어둡지만 가시성 문제는 없습니다.

**예외 한 가지 — 경고**: `--amber: #ffa62e`.
브랜드 팔레트는 아이덴티티 색이지 시스템 상태색까지 규정하지 않고,
오류를 브랜드색으로 칠하면 브랜드가 오염됩니다.

| 상태 | 색 |
| --- | --- |
| 검증 통과 | 마젠타 |
| 경고 · 부분 캐치 · 실패 | 앰버 |
| 근거 부족 · 제외 | 색 없이 **점선 테두리** |

### 5.1.1 화면당 마젠타는 하나의 역할만

**모두가 강조면 아무것도 강조가 아닙니다.** 한 화면에서 마젠타가 맡는 의미를
하나로 정하고, 나머지는 무채색으로 둡니다.

| 화면 | 마젠타가 뜻하는 것 |
| --- | --- |
| 질문하기 | 실행(캐치 버튼) |
| 캐치하는 중 | 진행된 구간 |
| 캐치 결과 | 찾은 수 · 시그널 |
| 액션 | **바뀌는 것**(TO-BE 에 새로 생기는 항목)과 주 실행 버튼 |

색 단계는 셋을 넘기지 않습니다. **무채색이 기본, 마젠타는 그 화면의 강조 하나,
앰버는 위험과 빗나감.** 배지·태그·진행 바까지 전부 마젠타로 칠하면 강조가 흩어집니다.

### 5.1.2 카드는 면이 필요한 것에만

카드가 모든 것을 감싸면 위계가 사라지고 “AI 가 만든 화면”처럼 보입니다.

| 쓸 것 | 쓰지 말 것 |
| --- | --- |
| 시안·목업처럼 **면 자체가 의미**인 것 | 수치 비교 — **표**가 본업입니다 |
| 근거 드로어처럼 겹쳐 뜨는 것 | 문단 — 그냥 문단으로 둡니다 |
| 저니 보드처럼 프레이밍이 필요한 것 | 목록 — 구분선으로 충분합니다 |

액션 화면은 이 원칙으로 카드 18개를 **시안 2장 + 표 1개**로 줄였습니다.

### 5.2 타이포그래피

| 역할 | 서체 | 굵기 |
| --- | --- | --- |
| Display | **Gasoek One** | 400 (단일) |
| Body | **IBM Plex Sans KR** | 400 · 500 · 600 |
| Data | **IBM Plex Mono** | 400 · 500 |

- Display 는 워드마크, 화면 제목, 결과 헤드라인, 검증 기록 제목, "찾았다!" 에만.
- **Gasoek One 에 700 을 지정하면 가짜 굵기로 뭉개집니다.** 반드시 400.
- 본문 기본 굵기는 400. 300 은 어두운 배경에서 획이 날아갑니다.

### 5.3 모션

| 대상 | 규칙 |

## 6. 개발 시 함정

### 6.1 legacy `globals.css` 가 전역에 로드됩니다

`layout.tsx` 가 앱 전체에 불러오므로 **밝은 테마 기준 전역 규칙이 새 화면으로
샙니다.** 실제로 겪은 사례:

- `table { min-width: 880px }` → 415px 드로어 안의 표가 밖으로 밀려남
- `th { background: #f2f6f5 }` → 다크 화면에 밝은 띠
- `th { text-transform: uppercase }` → `query` 가 `QUERY` 로
- `tbody tr:last-child td { border-bottom: 0 }` → 선이 반쪽만 남음

`catcher.module.css` 에서 `.app` 스코프로 무효화해 두었습니다.
**새 화면에 표나 폼을 추가할 때 같은 함정을 확인하세요.**

### 6.2 전역 `:focus-visible` 과 명시도 동점

`.app :focus-visible` 이 `(0,2,0)` 입니다. 입력 자체의 링을 지우고 감싼 튜브만
빛나게 하려면 **`(0,2,0)` 을 넘겨야** 합니다.

```css
/* ✗ 동점이라 순서에 밀림 */
.modalInput:focus-visible { outline: none; }
/* ✓ */
.modalForm .modalInput:focus-visible { outline: none; }
```

### 6.3 같은 규칙에 `color` 를 두 번 쓰지 않기

`.brand` 에 `color` 가 두 번 들어가 뒤의 값이 이겨 로고가 의도와 다른 색으로
렌더된 적이 있습니다. 토큰을 바꿀 때 죽은 선언이 남지 않았는지 확인하세요.

### 6.4 SVG 는 replaced element

`left` + `right` 를 함께 줘도 늘어나지 않고 **내재 비율 폭**을 씁니다.
저니 연결선 오버레이가 이 때문에 좁게 그려졌습니다.
`width: calc(100% - var(--label))` 처럼 명시 폭을 주세요.

### 6.5 `forEach` 안의 `return` 은 루프를 멈추지 않습니다

`playFrom()` 에서 이 실수로 엣지케이스 분기 후에도 나머지 단계가 계속
예약됐습니다. 단계 루프를 고칠 때는 `for...of` + `break` 를 유지하세요.
