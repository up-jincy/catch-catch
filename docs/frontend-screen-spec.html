Position

왜 대화형 UI를 버리는가

신청서의 STEP 1은 “Search / Chat Interface”라고만 적혀 있습니다. 해커톤에 나오는 거의 모든 Agent 프로토타입이 여기서 같은 화면을 만듭니다.

캐치캐치는 대화가 아니라 탐색을 팝니다. CX 담당자는 Agent와 수다를 떨고 싶은 게 아니라, 질문 하나를 던지고 검증된 답과 그 근거를 받고 싶습니다. 그래서 화면을 세 개로 고정합니다.

한 줄 정의

질문 하나 → Agent가 일하는 과정을 실시간으로 보여줌 → 근거까지 열어볼 수 있는 결과 한 장. 채팅 로그를 스크롤해서 답을 찾는 경험을 만들지 않습니다.

기존 화면은 지우지 않았습니다

동료가 만든 Working Demo 는 /legacy 경로에 그대로 살아 있고, Playwright e2e 6개도 진입 경로만 바꿔 전부 통과합니다. 새 화면은 / 에 올라가 있으며 src/features/signal-catcher/ 안에서만 동작합니다.

de-risk

useRunController() 하나가 question, startDate, endDate, enabledSources, runState, run(), openEvidence()를 모두 반환합니다. 새 화면은 이 훅에만 붙으면 되고, 백엔드 담당자는 이 작업 동안 아무것도 바꾸지 않아도 됩니다.

추가하는 의존성

motion 하나만 추가합니다. 화면 전환, 하트 스케일아웃, 저니 노드 stagger를 CSS 타이밍으로 손조율하면 시간이 다 날아갑니다. 심박 라인 자체는 stroke-dashoffset CSS 애니메이션이라 라이브러리가 필요 없습니다.

라우팅은 Next 라우트로 쪼개지 않고 한 페이지 안에서 phase 기반 뷰 전환으로 갑니다. 하트가 커지며 결과로 넘어가는 연출이 라우트 경계를 넘으면 끊깁니다.

Design system

LG유플러스 2025 리브랜딩 위에 얹기

사내 해커톤이라 회사의 새 브랜드 시스템을 그대로 씁니다. 공식 5색 밖의 색은 하나도 만들지 않았고, 파생값도 이 5색의 color-mix 로만 뽑았습니다.

팔레트 밖 색은 딱 하나

경고에만 앰버 #ffa62e 를 씁니다. 브랜드 팔레트는 아이덴티티 색이지 시스템 상태색까지 규정하지 않고, 오류를 브랜드색으로 칠하면 브랜드가 오염됩니다. 마젠타와 색상환에서 충분히 떨어지면서 같은 밝기대에 있는 색으로 골랐습니다.

밝은 바탕을 쓰지 않은 이유

Light Gray 를 바탕에 깔아 봤더니 마젠타가 막대·칩·헤드라인 한 단어 정도로만 나타나 브랜드 컬러가 화면을 끌고 가지 못했습니다. 포인트 색으로 밀려나 매력이 반감됩니다.

U+ Black 을 바탕에 깔고 U+ Light Gray 를 글자로 쓰면 여전히 공식 5색인데 마젠타가 발광합니다. 팔레트가 밝아야 한다는 규칙은 없습니다. 본문 대비는 13:1, 흐린 글자도 4.6:1 로 어둡지만 가시성 문제는 없습니다.

서비스 마크

돋보기 렌즈 안에 시그널 파형이 들어가고, 오른쪽 위에 작은 하트가 붙습니다. 돋보기 = 찾는다, 파형 = 시그널, 하트 = 찾았다로 서비스 전체가 마크 하나에 들어갑니다. 하트는 전환 연출에서 터지는 하트의 복선이기도 합니다.

렌즈와 손잡이는 크림색이고 하트만 Bright Magenta 로 빠져나옵니다. 마크에서 유일한 유채색이라 작게 놓여도 눈에 걸립니다.

노출은 상단 좌측 한 곳뿐

로고를 화면 곳곳에 반복하면 브랜드가 강해지는 게 아니라 닳습니다. 서비스 마크는 상단 좌측 서비스명 자리에만 둡니다. 캐치 버튼은 평범한 돋보기 아이콘, 로딩 화면의 질의 바와 결과 헤드라인은 아이콘 없이 텍스트만 씁니다.

상단 우측은 SaaS 관례를 따라 환경 배지 자리로 씁니다. PROTOTYPE 배지와 by 네박자를 나란히 두어 “아직 프로토타입”과 “누가 만들었나”를 한 줄로 전달합니다. 팀 이름 네박자(기획 2 · 개발 2)는 로딩 화면의 심박 라인과도 맞물립니다.

Screens

세 화면

손그림에서 열려 있던 질문 중 상당수는 백엔드가 이미 답을 갖고 있었습니다.

1

질문하기

phase = idle

상단에 “고객의 시그널을 찾아보세요”, 가운데 입력창 하나, 아래 제안 시나리오 카드. 그 외에는 아무것도 두지 않습니다.

  • 확정 Placeholder 타이프라이터. 페르소나별 질문이 타자 치듯 나타났다 지워집니다. 실제 placeholder 속성 대신 오버레이 요소로 구현하고, 사용자가 입력을 시작하면 즉시 멈춥니다.
  • 확정 + 버튼 → 2depth 컨텍스트 메뉴. Dataset >에서 연결된 데이터가 전부 선택된 상태로 열리고 개별 해제가 가능합니다. search_history만 필수 고정.
  • 확정 기간은 자연어가 아니라 칩. + → 기간 >에서 최근 7일 / 14일 / 30일 / 직접선택. 선택하면 입력창 앞에 최근 14일 × 토큰 pill로 박힙니다.
  • 제외 자연어 날짜 파싱. RunRequest가 ISO start_at/end_at을 요구하는데 백엔드에 파서가 없습니다. 프론트에서 파싱하면 데모 중 깨질 위험만 커집니다.

Dataset 2depth에 실제로 띄울 수 있는 것

GET /api/sources가 소스별로 label, description, supported_topics, data_interval까지 내려줍니다. 그래서 밋밋한 체크박스 대신 “이 소스가 커버하는 주제” 뱃지 + 데이터 보유 기간을 함께 보여줍니다. 연결된 데이터가 진짜라는 인상이 여기서 만들어집니다.

2

캐치하는 중

phase = running

상단에 질문이 고정되고, 가운데 심박 라인이 단계마다 채워지며, 그 아래로 진행 문장이 크레딧처럼 흘러 올라갑니다. 다 찾으면 하트가 터지며 결과 화면으로 넘어갑니다.

확정 · 백엔드가 이미 보내고 있음

로딩 단계를 새로 정할 필요가 없습니다. 백엔드가 이미 이 순서로 SSE 이벤트를 스트리밍하고 있고, 각 이벤트에 화면에 그대로 띄울 수 있는 실제 문장이 들어 있습니다. 타이머로 흉내 내는 게 아니라 진짜 Agent 진행상황을 노출합니다.

차별점

report_validating = “근거 검증” 단계를 로딩 화면에 노출하는 것. “AI가 지어낸 게 아니라 14개 주장을 대조해 12개만 남겼다”를 사용자가 기다리는 동안 보게 됩니다. LLM 결과를 그냥 뱉는 다른 팀 데모와 갈리는 지점입니다.

심박 라인이 곧 스테퍼입니다

처음에는 심박 라인과 5칸 스테퍼를 따로 뒀는데 시선이 두 갈래로 갈렸습니다. 원형 게이지로 합치는 안도 시도했지만 심박의 “살아 있는” 느낌이 사라졌습니다. 결론은 박동 하나 = 단계 하나입니다.

  • 확정5개의 박동이 이어져 하나의 심박 라인을 이룹니다. 단계가 끝나면 그 구간이 마젠타로 그려진 채 남고, 아직 오지 않은 구간은 회색 평선입니다.
  • 확정진행 중인 박동은 그 단계의 소요시간에 맞춰 실시간으로 그려지는 중입니다. 라벨(목표·계획·분석·인사이트·검증)은 각 박동 바로 아래에 붙습니다.
  • 확정진행이 멎으면(확인 대기·실패) 그리던 박동도 그 자리에 멈추고 회색으로 바뀝니다. 실패 시에는 평선으로 떨어집니다.

진행 문장은 크레딧처럼 흐릅니다

한 줄만 바꾸면 “지금 일하고 있다”는 증거가 남지 않습니다. 지나간 문장이 위로 밀려 올라가며 마스크로 서서히 지워지고, 현재 문장이 가장 선명합니다.

  • 확정등속 크레딧은 폐기. 문장 도착 간격이 350ms~2400ms 로 제각각이라 등속으로 흘리면 가장 중요한 검증 문장이 읽히는 중에 지나가 버립니다.
  • 확정계단식 스크롤. 문장이 도착할 때만 스택이 한 줄 밀려 올라가고, 현재 문장은 항상 같은 자리에 멈춰 있습니다.
  • 확정현재 문장 앞에 단계 칩(검증)이 붙어 단계명과 세부 문장이 한 줄로 합쳐집니다. 지나간 줄은 ✓ 로 바뀝니다.
  • 확정질문은 콘텐츠가 아니라 맥락이므로 중앙 스택에서 빼 상단 튜브에 고정합니다.

단계별 체류 시간

문장마다 머무는 시간을 따로 줍니다. 데이터를 훑는 구간은 기계 속도로 흘려보내고, 결론과 검증만 사람이 읽을 수 있게 잡아 둡니다.

단계시간성격
목표1.3초훑는 속도
계획0.9초훑는 속도
분석1.9초5문장이 후루룩
인사이트2.1초읽는 속도
검증3.5초마지막 문장 혼자 2.4초

총 10.9초. 앞 세 단계가 38%, 인사이트와 검증이 62%를 차지합니다. 심박이 그려지는 속도도 같이 따라가서 “빠르게 훑고 → 신중하게 검증한다”가 애니메이션으로 읽힙니다.

  • 확정 하단 시그널 강도 라인. 저니맵의 감정 곡선이 놓이는 자리에 signals[].contribution으로 계산된 실제 강도 곡선을 깝니다. 곡선이 치솟는 지점이 곧 개입해야 할 시점입니다.

디자인 씽킹 유저 저니맵으로 가야 할까

결론은 격자는 안 가져오고, 서사 장치만 가져옵니다.

저니맵은 페르소나 한 명의 일반화된 여정을 워크숍에서 합의해 만드는 산출물입니다. 가로축이 “인지 → 탐색 → 가입 → 이탈” 같은 추상 단계이고, 세로에 행동·생각·감정·터치포인트가 놓입니다. 반면 우리 데이터는 타임스탬프가 찍힌 실제 이벤트 로그입니다.

저니맵 격자를 쓰면 생기는 문제

감정 곡선 칸을 채우려면 데이터에 없는 고객의 감정을 지어내야 합니다. 그 순간 “모든 주장은 원본 데이터로 검증된다”는 우리 팀의 최대 강점과 정면으로 충돌합니다. 검증할 근거가 없는 곡선을 화면에 올리는 건 우리가 하지 말아야 할 일입니다.

대신 저니맵에서 강도 곡선(→ 시그널 강도 라인)과 국면 구분(→ Phase 밴드)은 가져올 수 있습니다. 둘 다 데이터로 뒷받침될 때만 넣습니다. Phase 밴드는 분류 규칙을 기획에서 정의해줘야 하므로 아래 기획 확인 항목으로 넘겼습니다.

Depth

결론까지의 과정을 보고 싶은 사용자

손그림 맨 위의 “evaluation — 이걸 어떻게 넣지?”에 대한 답입니다. 근거 검증은 우리 팀이 다른 팀과 갈리는 지점이자 기술적으로 가장 어려운 부분인데, 지금 화면 어디에도 자리가 없습니다.

문제는 모든 사용자가 이걸 보고 싶어 하지는 않는다는 겁니다. CX 담당자는 “37명”만 필요하고, 데이터 담당자와 심사위원은 “왜 37명인지”를 끝까지 파고 싶어 합니다. 그래서 하나의 화면에 다 넣지 않고 깊이를 3단으로 나눕니다.

Tier 1기본

근거 칩

결과 화면의 모든 문장 끝에 근거 3 같은 작은 칩. 기본 모드에서는 hover할 때만 드러나 읽기를 방해하지 않습니다.

여기서 멈추는 사용자가 대부분이고, 그래도 괜찮은 화면이어야 합니다.

Tier 2궁금할 때

근거 드로어

칩을 누르면 우측에서 슬라이드. 이 문장이 어떤 Fact에서 나왔는지, 어떤 Source의 몇 건 데이터인지, 원문 스니펫까지.

맥락을 잃지 않도록 페이지 이동 없이 겹쳐서 엽니다.

Tier 3딥다이브

검증 기록 — 별도 전체 화면

Run 하나의 Goal → Plan → Step → Fact → Claim → Report 계보 전체. 결과 화면 하단의 이 결론이 나온 과정 보기 →로 진입하고, 자체 URL을 갖습니다.

드로어에 욱여넣지 않고 페이지를 분리하는 이유: 이건 읽는 화면이 아니라 파고드는 화면이고, 링크로 공유돼야 하기 때문입니다.

백엔드가 이미 지원함

GET /api/run-artifacts/{run_id}로 완료된 Run의 Artifact 전체를 다시 꺼낼 수 있고, /document, /download.json, /download.md까지 있습니다. 즉 검증 기록 페이지는 Run이 끝난 뒤에도 열리는 영속 URL이 되고, “이 분석 결과를 링크로 팀에 공유하세요”가 데모에서 실제로 동작합니다.

Edge cases

안 만들면 데모 중 멈추는 것

백엔드가 보내는데 지금 화면에 대응이 없는 상태들입니다.

01 · clarification_required — 심문 모달

Agent가 되물을 수 있습니다. 대화형 UI를 안 하기로 했으니 인터럽트 한 장으로 받는데, 이 순간을 약점이 아니라 연출로 씁니다. 사용자가 Agent와 대화하는 게 아니라, 탐정이 단서를 좁히는 장면이 되게 합니다.

  • 연출심박이 멈춥니다. 로딩 라인이 flatline으로 떨어지고 화면이 한 톤 어두워집니다. 진행이 멈췄다는 게 텍스트 없이 읽힙니다.
  • 연출Agent 질문이 타이핑되며 나타납니다. 첫 화면 placeholder와 같은 모션 언어라 “같은 Agent가 말을 건다”는 인상이 이어집니다.
  • 연출블록 커서. 입력 캐럿을 #ff2e98 블록 커서로. 모노 폰트 입력창, 좌측에 > 프롬프트 기호.
  • 카피“잠깐, 하나만 더 확인할게요” → 답변 전송 → 심박이 다시 뛰기 시작하며 스테퍼가 이어집니다.
  • 주의브라우저 기본 alert/confirm은 쓰지 않습니다. 커스텀 dialog에 focus trap을 걸고, 백엔드가 대기 중이므로 “나중에 답하기”는 두지 않습니다.

02 · unsupported_analysis — 오류가 아니라 안내

범위 밖 질문일 때 suggested_questions[]가 함께 내려옵니다. 첫 화면으로 되돌리면서 사용자가 쓴 질문은 입력창에 그대로 남기고, 그 아래 제안 시나리오 카드를 suggested_questions[]로 교체합니다.

경고색을 쓰지 않는 이유

이건 실패가 아니라 Agent 가 “이건 못 하지만 이건 할 수 있어요”라고 말을 거는 상황입니다. 경고색을 쓰면 사용자를 탓하는 톤이 됩니다. 서비스 마크를 붙인 브랜드 톤(마젠타) 안내 박스로 처리하고, 아래 대안 카드로 바로 이어지게 합니다.

03 · degraded / failed — “부분 캐치”로 프레이밍

실패를 숨기지 않는 게 우리 팀 정체성과 맞고, 심사에서도 유리합니다. 다만 실패처럼 보이지 않게 프레이밍합니다.

  • 헤드라인“328명을 찾았어요 — 다만 2개 소스는 확인하지 못했어요”. 찾은 것을 먼저 말하고 못 한 것을 뒤에 붙입니다. 상단 배지는 부분 캐치(amber).
  • 지표근거가 부족한 지표 카드는 숫자를 지어내지 않고 회색 점선 테두리 + “근거 부족”으로 비워 둡니다. 빈 카드 하나가 나머지 숫자의 신뢰를 올립니다.
  • 설명limitations[]를 페이지 맨 아래가 아니라 상단 배지를 누르면 펼쳐지는 패널로. “무엇을 확인하지 못했나”를 찾아 헤매게 하지 않습니다.
  • 회복“VOC를 추가해서 다시 캐치하기” 버튼. 빠진 소스를 켠 채 같은 질문으로 재실행합니다. 실패를 막다른 길이 아니라 다음 행동으로 잇습니다.
  • 완전 실패failed는 화면을 자동으로 바꾸지 않고 로딩 화면에서 멈춰 세웁니다. 자동으로 첫 화면에 돌려보내면 사용자가 왜 돌아왔는지 알 수 없습니다. 평선이 된 심박이 어느 단계에서 끊겼는지 그대로 남고, 그 아래 연결 끊김 앰버 배지 · 사유 · [다시 캐치하기] [질문 바꾸기] 두 버튼을 답니다. 모달로 덮지 않는 이유는 평선을 가리기 때문입니다.

오버레이는 화면 전환 래퍼 밖으로

근거 드로어와 모달이 스크롤을 내린 상태에서 화면 밖에 그려지는 문제가 있었습니다. 화면 전환 애니메이션이 animation-fill-mode: both 로 끝난 뒤에도 래퍼에 transform 이 남는데, transform 이 있는 조상은 position: fixed 의 기준점이 됩니다. 그래서 오버레이가 뷰포트가 아니라 페이지 전체를 기준으로 붙었습니다.

시연용 URL 파라미터

발표 중 각 상태를 즉시 재현하기 위한 스위치입니다. URL 만 열면 질문을 입력하지 않아도 그 상태로 바로 들어갑니다. 백엔드를 붙이면 이 분기는 실제 이벤트로 대체됩니다.

파라미터용도
?pause=goal|plan|analyze|insight|verify|complete|clarify로딩 화면을 그 시점에 정지. 진행 중인 박동은 절반쯤 그린 상태로 멈춤
?speed=0.25 ~ 3전체 진행 속도 배수. 0.5 면 5.5초, 1.5 면 16초
?burst=lens전환 마크를 하트 대신 돋보기로
?clarify=1확인 대기(심문 모달) 재현
?degraded=1부분 캐치 — 배지 + “근거 부족” 점선 카드
?failed=1실패 — 평선으로 떨어진 뒤 첫 화면 복귀(입력값 보존)
?unsupported=1범위 밖 질문 — 대안 질문 카드로 교체

조합도 됩니다. ?clarify=1&degraded=1 이면 확인 대기 후 부분 캐치 결과로 이어집니다.

기획에 확인이 필요한 것

화면 구조는 정해졌지만, 그 안에 들어갈 말과 판단 기준은 기획이 정해줘야 합니다.

  • 이름은 이렇게 적용했습니다 — 확인만 부탁드려요. 공식 명칭은 고객 시그널 캐처(Customer Signal Catcher), 화면에 노출되는 서비스명은 캐치캐치로 적용했습니다. 헤더는 “캐치캐치 / CUSTOMER SIGNAL CATCHER” 두 줄입니다.
  • 전환 마크 — 하트 vs 돋보기, 어느 쪽인가요? 기본은 하트이고 ?burst=lens 로 돋보기 버전을 바로 볼 수 있게 해 뒀습니다. 제 의견은 하트입니다 — 돋보기는 로고·상단 질의 바·결과 헤드라인에 이미 세 번 나와 반복이고, 돋보기 = 찾는 중 / 하트 = 찾았다로 의미가 갈립니다. 다만 취향 영역이라 팀 의견을 받고 싶습니다.
  • 로딩 10.9초, 발표 호흡에 맞나요? 앞 세 단계는 훑는 속도로 줄이고 인사이트·검증만 잡아 뒀습니다. 리허설에서 길다고 느껴지면 ?speed=0.8(8.7초)까지는 여유가 있습니다. 그 아래로 가면 분석 단계 문장이 280ms 라 글자가 깜빡이는 것처럼 보입니다.
  • 제안 시나리오 카드 4개의 최종 문구. 신청서 대표질문 4개를 그대로 쓸지, 페르소나 태그(CX · CRM · 서비스기획 · 상담운영)를 붙일지. 첫 화면에서 사용자가 처음 읽는 문장이라 데모 첫인상을 결정합니다.
  • 결과 헤드라인의 톤 가이드. “37명의 고객 시그널을 찾았어요”처럼 수 중심으로 갈지, “반복 검색 후 상담으로 넘어간 고객 37명”처럼 패턴 중심으로 갈지. LLM이 생성하는 문장이라 프롬프트에 넣을 규칙이 필요합니다.
  • 저니 Phase 밴드를 넣을까요? 넣는다면 국면 이름(예: 문제 발생 → 자가 해결 시도 → 도움 요청 → 이탈 검토)과, 어떤 topic·outcome이 어느 국면인지 분류 규칙을 기획이 정의해 줘야 합니다. 규칙을 못 정하면 넣지 않습니다 — 지어낸 국면은 근거가 없습니다.
  • “근거 부족”을 어디까지 드러낼까요? 검증되지 않은 지표를 빈 카드로 남기는 게 우리 강점이지만, 심사 자리에서는 미완성처럼 보일 위험도 있습니다. 노출 수위를 합의해 두면 데모 중에 흔들리지 않습니다.
  • Action Preview의 범위가 이대로 맞을까요? 신청서 9장에 “추천검색어 적용하기 → 설정 화면 → 적용 완료”를 Mock UI로 구현한다고 명시돼 있어 그대로 만들었습니다. 추천검색어 액션만 실행 화면을 갖고, 나머지 액션은 “다음 단계” 라벨로 둡니다. 적용 완료 화면에 “실제 운영 시스템에는 반영되지 않았어요”를 명시했는데, 시연에서 이 문구를 남길지 뺄지 정해 주세요.
  • 데모 시연 스크립트 — 로밍 질문 하나로 고정할까요? 신청서 MVP Scenario를 따라 “최근 로밍을 알아보는 고객들이 가장 많이 궁금해하는 게 뭐야?” 하나로 목업을 만들었습니다. 결과는 “단기 일본 여행 로밍을 고르지 못한 고객 328명”입니다. 두 번째 질문도 시연할지, 이 하나에 3분을 쓸지 정해 주세요.
  • 분석가 모드의 기본값. 항상 기본 모드로 시작할지, 마지막 선택을 기억할지. 시연 순서(기본 → 분석가 → 검증 기록)와 직결됩니다.

백엔드에 확인이 필요한 것

화면은 다 만들어졌고, 아래가 풀려야 STEP 6(실연결)을 끝낼 수 있습니다.

  • 대표 질문 하나의 fixture 응답 전체를 JSON 으로 주세요. 가장 먼저 필요합니다. 지금은 Mock 이 CatchSession 을 만들고 있고, 같은 모양을 실제 이벤트로 채우면 화면은 그대로 동작합니다. mode=fixture 로 백엔드를 띄워 한 번 실행한 결과를 그대로 받으면 매핑을 바로 맞출 수 있습니다.
  • headline에 고객 수가 항상 들어가나요? 결과 화면 첫 타이포가 “N명의 고객 시그널을 찾았어요”입니다. 숫자를 별도 필드로 받을 수 있으면 타이포를 훨씬 크게 쓸 수 있습니다.
  • representative_journeys는 몇 명 분량인가요? 스윔레인은 한 번에 한 고객을 그립니다. 여러 고객이 섞여 오면 customer_id 기준으로 나눌 수 있어야 합니다.
  • clarification_required는 실제로 얼마나 자주 발생하나요? 데모 시나리오에서 뜬다면 UI 우선순위를 STEP 3으로 올려야 합니다.
  • 검증에 실패한 claim도 내려오나요? 가장 중요한 질문입니다. findings[]에 통과한 claim만 담긴다면 스코어카드가 항상 100%가 되어 의미가 없어집니다. 검증 결과(통과/탈락)와 탈락 사유를 함께 받을 수 있으면 “14개 중 12개 통과, 2개는 근거 부족으로 리포트에서 제외”라고 쓸 수 있고, 이게 우리 팀 차별점을 가장 강하게 보여주는 문장입니다.
  • RunArtifact에 계획 수정 이력이 남나요? Run이 끝난 뒤 검증 기록 페이지를 다시 열었을 때 plan_revised가 몇 번 있었는지, 어떤 계획이 어떻게 바뀌었는지 복원할 수 있어야 스코어카드의 “계획 수정 1회”가 성립합니다.
